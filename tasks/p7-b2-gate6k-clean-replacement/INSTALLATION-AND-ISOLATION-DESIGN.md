# Installation origin and isolation design

This is an investigated design, **not a tested installer or a provisioned guest**. Administrative access/capacity checks are blocked. No propagation operation is approved by this document. Gate 6K source and checks remain unchanged.

## Findings from the exact authenticated ISO

`evidence/iso-inspection.json` records a read-only ISO9660/Squashfs inspection of the original Ubuntu image whose SHA256 and signature reverified. `casper/install-sources.yaml` identifies `ubuntu-server-minimal` and the default layered `ubuntu-server` source. The minimal source already contains an empty root-owned0700 `/root/.ssh`. `/etc/skel` has ordinary shell dotfiles; no `.ssh` appears there. The inspected base includes empty `/etc/credstore` and `/etc/credstore.encrypted` directories. The normal server overlay has no matching additional paths in this inspection. This is public image metadata, not a claim about VM163's files or its history. The listing is not a comprehensive secret detector.

The image manifests identify cloud-init/cloud-init-base `26.1-0ubuntu3~26.04.1`, systemd `259.5-0ubuntu3.4`, and openssh-client `1:10.2p1-2ubuntu3.5` in the base. Its cloud configuration includes users/groups and SSH stages, SSH import and later scripts. The saved image's `cc_ssh.py` calls `setup_user_keys` for the default user and root even with an empty supplied key set; the saved `ssh_util.py` creates authorized-key paths/files as part of that operation. This explains how installer/first-boot behavior can create SSH metadata without an operator importing a key. It does **not** prove VM163 has no keys.

[Subiquity documents](https://canonical-subiquity.readthedocs-hosted.com/en/latest/reference/autoinstall-reference.html) separate controls for installing sshd, authorized keys, identity and merged target cloud user-data. Turning `install-server` off only controls the server package; it neither removes the image's empty directory nor proves cloud modules will not run. Cloud-init's cache can preserve datasource inputs; the [cache documentation](https://docs.cloud-init.io/en/latest/development/internal_files.html) supports treating unknown cache as unresolved provenance.

## Installation-time prevention

Use only the pinned original ISO and reviewed public inputs, without cloning/importing an existing installed VM. No NoCloud/config-drive, SSH import, network datasource, provider credentials, online installer refresh, network updates, snaps, drivers, Ubuntu Pro attachment or additional unreviewed installer scripts. No NIC is attached at any time. Select the exact OS source from the signed image's own source inventory.

The unchanged r1 gate refuses `/root/.ssh` merely existing. Therefore **a stock installation from this ISO is not an implementation of the requested ready lab**. A suitable build needs a recorded installation-time image-construction procedure that omits only the proven-empty image directory before the target root is materialized, records the original image metadata and all derivative hashes, and never removes a directory from a running guest to clear the scanner. Any unexpected child, link, key, host key or modified image stops that procedure. This selective-construction implementation is still pending; a generic Subiquity flag accomplishing it has not been established. Do not present an untested extraction/exclusion command as a supported installer. An alternative scanner policy release would need separate engineering approval and new source/release review; this task does not propose a scanner exception as a shortcut.

Before the **first target boot**, create the documented [cloud-init disabled sentinel](https://docs.cloud-init.io/en/latest/howto/disable_cloud_init.html) as part of construction, exclude datasource/seed injection by design and provision identities directly through the reviewed offline installer. Disabling on a guest that has already booted would not establish clean history. The sentinel prevents later execution; it does not erase a cache already supplied by an installer. Inventory any installer-created cache before first boot and retain exact public input/generator provenance. If Subiquity supplies target seed data, account for each generated file and its original permissions; do not clear or chmod unknown cache afterward. If the unchanged gate refuses those files, stop and revise the construction procedure on a fresh target.

Record each input file/hash and each command, source-image extraction/filter rule, account creation, hostname/machine-id generation, bootloader/kernel installation and first-boot transition. A modified installation medium is a derivative with its own digest and transformation record, never an Ubuntu-signed derivative. Preserve the original signed media unchanged. Do not broadly exclude package files, logs, credential directories or systemd units to hide a failure. Actual boot/kernel/installer rehearsal is still required; none occurred here.

## Console, identities and runtime

Trusted control is the operator's existing authenticated Proxmox management console. Record the actual account/session reference without tickets or secrets. Do not embed a reused password, SSH key, provider secret or default shared password in installer data. All imported roles must start without credentials; establish a documented console-root bootstrap from the trusted installer/rescue path. Installed-console authentication/root-session continuity is an unresolved implementation detail: no persistent root autologin/debug-shell policy is silently enabled. Its chosen method must work after normal boot before qualification; a chroot/live installer view is not a valid guest preflight.

Create `jarvis` only if the existing preparation tools need that account; no old home contents. Create `g6j-operator`, `g6j-service`, `g6j-agent` with distinct nonzero UIDs and distinct private GIDs, locked passwords, non-login shells and no supplemental/admin memberships. Do not force VM163's numeric UIDs (999/995/994) into occupied IDs. Record the actual values and use them in the later approved test. Root is the fourth authority principal. Inspect effective sudo/polkit grants without publishing their configuration. Preparation must not leave test identities with install/admin rights.

The sealed dependency installer is explicitly **unprivileged** and refuses root. It provides a reproducible runtime fixture, not a root-protected `/opt/g6j-venv` installation. Use it only for its documented role after verified offline extraction. Do not edit its manifest, bypass its refusal, install every deb globally or copy Nexus's/VM163's runtime tree. A root-reviewed installation stage must independently materialize the exact public runtime/dependencies into exclusive protected paths, or copy an accounted fresh build after excluding all writers and stale writable descriptors. Root-owned imports must not resolve into a preparation user's work tree. Recreating a venv at the final path is necessary if relocation leaves absolute interpreter/library paths; blind `mv`/chown is not proof.

Destination plan: root-owned `/opt/g6j-venv` and any interpreter/native-library backing tree; root-owned `/opt/g6k-preflight-r1` from the pinned safe extractor; root-owned `/opt/g6k-offline` with exactly131 public files plus `ARTIFACTS.json`. All ancestors and resolved symlink targets must be root-controlled, not group/world writable. Native library maps must demonstrate the pinned SQLite/libseccomp/crypto origins. Generate and retain a protected installed-runtime file inventory, check pip metadata plus actual versions/imports, and verify the unchanged release's dependency check. No arbitrary executable transfer from VM163 is permitted. These protected provisioning steps remain **not implemented or executed for a replacement**.

Fresh public transport is `/home/nexus/.local/share/jarvis-g6k-clean-replacement`. It is user-owned staging only. Mount approved read-only transfer media only during setup; retain manifest/digests, copy public bytes exclusively to fresh root-owned guest destinations, independently rehash, normally unmount the exact observed mounts and detach media from the **new VM only** before preflight. Busy unmounts stop; never force/lazy-unmount. No writable host share, bind mount or disk from any existing VM is acceptable. Preserve failures rather than replacing/removing them.

## Systemd credential mounts

Systemd may create per-service read-only credential mounts when a unit uses credential directives. Empty protected containers/mounts are not proof of imported secrets; populated files remain a separate fail-closed finding. The [upstream execution documentation](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html) describes loading/importing credentials and protected per-unit directories. Verify actual guest units and metadata against the installed version: current upstream documentation describes a newer systemd and is mechanism evidence, not a version-specific attestation.

Supply no fw_cfg/SMBIOS credentials, host credential passthrough, credstore payloads or installer secret seeds. Preserve and inventory empty stores and runtime mounts; inspect types/owners/modes/counts without opening credential payloads. Do not stop credential-using services or unmount a credential store to obtain a clean report. Any regular credential payload, even empty/root-only, refuses under r1 and needs an installation-origin explanation before revising a fresh build.

## Explicit propagation policy decision, still required

[Systemd startup](https://github.com/systemd/systemd/blob/main/src/shared/mount-setup.c) normally changes root propagation recursively to shared. A new VM does not automatically satisfy r1's all-private requirement. [Kernel propagation semantics](https://docs.kernel.org/filesystems/sharedsubtree.html) distinguish private, shared and slave relationships. Private flags do not prove there are no host shares, credential payloads or unsafe underlying files.

Recommended review option **H5-N**: after independently excluding all host/network shares and detaching transfer media, explicitly approve a temporary mount-only namespace for the qualification **process tree**. No user/PID/network namespace mapping, persistent namespace mount or hidden directories. PID1's namespace remains unchanged/shared; every check and the eventual authorized runner must execute in that same temporary namespace and record both namespace IDs/boot ID. [util-linux documents](https://man7.org/linux/man-pages/man1/unshare.1.html) the namespace lifetime and propagation behavior. This scope is eligible only if the human policy owner accepts process-tree isolation. Closing a shell does not undo filesystem mutations or necessarily release surviving descendants.

Alternative **H5-G**: if policy requires guest-wide privacy, review a recursive change in PID1's namespace, its service consequences and its actual all-mount result; other existing namespaces still need accounting. This is broader and requires explicit approval. Nonrecursive root-only privacy is insufficient. No persistent boot unit is proposed, and a reboot invalidates the observation. Do not claim `PrivateMounts=yes` alone gives r1 all-private topology or that making everything shared later exactly restores the original peer relationships.

**Neither scope is selected or authorized by this packet.** There is no automatic `unshare`, propagation mutation, service stop or qualification command in the supplied tools. The user's GO explicitly reserves the scope approval.
