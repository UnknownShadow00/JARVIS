# Dispatch Decision Matrix — Task 13B11K

**Status: FROZEN before the module was written.** The machine-readable table is
`dispatch-matrix.json`, generated by `freeze_matrix.py` and hashed in `frozen-hashes.txt`. The
scored test drives every cell against the real dispatcher and, where a confirmation exists, the
**real** `ConfirmationStore`, and compares six recorded fields per cell.

## Dimensions

* permission outcome (3): `ALLOW`, `REQUIRE_CONFIRMATION`, `DENY`
* confirmation setup (10): `absent`, `binding_absent`, `authority_absent`, `valid_pending`,
  `wrong_session`, `wrong_binding`, `expired`, `denied`, `cancelled`, `already_claimed`
* executor outcome (5): `success`, `error`, `timeout`, `exception`, `contract_violation`

3 × 10 × 5 = **150 cells**, plus **5 replay rows**.

## Recorded per cell

`executor_called`, `result_status`, `error_kind`, `executed`, `facts_source`,
`confirmation_state_after`, `gate_reached`.

## Shape of the frozen answer

| | count |
|---|---|
| cells | 150 |
| cells where the executor is called | **10** |
| `BLOCKED` | 95 |
| `CONFIRMATION_REQUIRED` | 45 |
| `SUCCESS` | 2 |
| `ERROR` | 6 |
| `TIMEOUT` | 2 |

Only the two dimensions that describe a fully valid authority — `ALLOW` + `absent`, and
`REQUIRE_CONFIRMATION` + `valid_pending` — ever reach the executor, once each per executor
outcome: 2 × 5 = 10.

The 90 `invocation_inconsistent` cells are the pairing rule doing its work: an `ALLOW` or `DENY`
invocation that carries a confirmation id is refused at gate 2, before its permission outcome is
even read, because that pairing is the shape a laundering attempt would have.

## Replay

Five rows, one per first outcome. In every one the second dispatch of the same invocation id is
`BLOCKED` / `invocation_already_dispatched` / `executed = false`, and the total executor call
count stays **1**.
