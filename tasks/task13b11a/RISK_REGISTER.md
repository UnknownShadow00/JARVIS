# Implementation Risk Register

**Status:** plan only. Severity is the impact if the risk materialises in production.

| ID | Risk | Severity | Likely trigger | Planned mitigation | Validation |
|---|---|---|---|---|---|
| R-01 | Operational raw-prose bypass — model text reaches the user on an operational turn | **Critical** | a new code path returns the model draft directly; an exception handler falls back to `str(exc)` prose; a "quick fix" for an unhandled obligation | separate types (`ModelDraft` vs `ApprovedOperationalResponse`); the server can only render the approved type; every operational fallback is a named obligation, never prose | CT-001, CT-012; audit assertion that `final_response_source != MODEL_RAW` on every operational turn |
| R-02 | Proposal executed before the permission decision | **Critical** | dispatcher called directly from the adapter or from legacy code during migration | only `dispatch.py` may call `registry.call` on the new path; `ToolInvocation` requires a `PermissionDecision` field to construct | CT-015; static check that `registry.call` has exactly two call sites |
| R-03 | Confirmation replay — an old approval executes again | **High** | duplicate `/confirm` POST, retried client, shared link | single-use record with a state machine; `PENDING → EXECUTING` under a lock; idempotency on `invocation_id` | integration test: double-confirm executes once |
| R-04 | Stale confirmation executes long after the request | **High** | no expiry today | `expires_at` per permission class; expired records move to `EXPIRED` on load and on access | unit test with a fake clock |
| R-05 | Confirmation bound to the wrong action | **Critical** | id collision (8-char slice today), argument mutation between request and approval | long opaque id; binding check on action, target, canonical args, session; re-derive canonical args at approval | CT-004 variant with two concurrent pending actions |
| R-06 | Provenance corruption — a model-derived value enters the ledger | **Critical** | a convenience helper writes model output as a `USER_FACT` | ledger write API takes only typed sources; no `record_from_text(model_output)` exists; review rule | unit test asserting no write path accepts model text |
| R-07 | Canonicalization mismatch — the user confirms X and Y executes | **High** | canonicalization applied after confirmation, or rule version changed between the two | canonicalize before permission and confirmation; store `canonicalization_version`; compare at approval | CT-010 + binding test |
| R-08 | Tool-result spoofing — model text parsed as a result | **Critical** | adapter parses model JSON into a result-shaped object | only `dispatch.py` constructs `TrustedToolResult`; the adapter returns `ToolProposal` only | CT-014 |
| R-09 | Audit gap on a safety-critical decision | **High** | async queue drops under load; audit failure swallowed | fail-closed for permission/confirmation/dispatch events; bounded queue; existing fallback write retained | fault-injection test with a failing writer |
| R-10 | Lifecycle loss of pending state | **Medium** | deep sleep exits the process (`resource_auto_deep_sleep_exit`) | persist confirmations append-only; on load, expire rather than execute; never auto-execute on resume | restart test with a pending confirmation |
| R-11 | Shared-Ollama unload kills the brain mid-turn | **Medium** | `unload_all_ollama_models` unloads every loaded model (`app/resource_manager.py:559`) | model-ownership policy (see the integration plan §24); in-flight turn treated as `TIMEOUT`, never as success | integration test that unloads during a turn |
| R-12 | Feature-flag leakage — new path runs when it should not | **High** | flag read in more than one place; partial reload mid-turn | single read at the top of the turn, carried in context; mode recorded in every audit event; default legacy on parse failure | unit test on config default; audit review |
| R-13 | Legacy regression — existing behaviour changes while the flag is off | **High** | refactor of `_process` instead of an added branch | additive-only change until P7; `pytest` + `evals` golden must stay 12/20 with the same eight failures | every phase |
| R-14 | Double execution across paths | **Critical** | both legacy and new path handle the same turn (e.g. shadow accidentally live) | the shadow pipeline receives an inert dispatcher instance; mode is exclusive by construction | shadow test with an audit-hook assertion of zero side effects |
| R-15 | Migration risk | **Low** | introducing a database for provenance/confirmation | v1 uses append-only JSON alongside existing `data/*.json`; no schema migration; files ignorable in legacy mode | startup test with missing/corrupt files |
| R-16 | Race conditions on the ledger or confirmation store | **Medium** | concurrent `/chat` and `/confirm`, or two sessions | per-session lock for ledger writes; per-record lock for state transitions; single-writer store | concurrency test |
| R-17 | Tool timeout ambiguity — the side effect may or may not have happened | **High** | slow tool, network partition | distinct `TIMEOUT` status; response must state uncertainty; no retry without an idempotency key | fault-injection test |
| R-18 | Rollback failure | **High** | new path leaves state legacy cannot read; flag not honoured | legacy reads nothing the new path writes; rollback tested as a drill at P7 and P9 | rollback drill recorded in evidence |
| R-19 | Permission matrix drift from operator intent | **Medium** | table edited during implementation | matrix is data, versioned, approved once by the operator; mismatches listed explicitly in the plan | review gate before P4 exit |
| R-20 | Over-templated assistant — operational answers feel robotic | **Low/Medium** | every turn routed operational | lane policy keeps explanation conversational; measure utility as in C5 (97.2% baseline) | A/B at P11 |
