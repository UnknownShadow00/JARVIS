# Narrow human authority, independently attributable

No public opening endpoint or API-token opening authority. REST/WS headers, continuation tokens, model outputs, timers, callbacks, source edits, missing files and restarts cannot authorize transitions. A socket0700 owned by jarvis is insufficient because Codex has that UID.

Recommended proposed model: a dedicated operator identity, per-action privileged authentication without cached/NOPASSWD authorization for jarvis/Codex, and a hardware-backed operator signing key requiring human presence/user verification outside the service/development environment. A fixed root-owned helper verifies a signed canonical approval, pinned operator public key, purpose and fresh challenge. The signing ceremony displays the exact operation and deployment/epoch/ordinal summary. Merely recording an operator name or checking peer UID/PID does not prove intentional human approval. Hardware/credential enrollment and constrained privilege policy are later separately approved work; no installed availability is claimed.

The helper exposes only fixed verbs: validate status, OPEN_HOLD, AUTHORIZE_ONE, TERMINAL_STOP. Deployment/retirement/lineage publication are separately authorized procedures, not hidden opener verbs. It accepts bounded structured fields from a protected reviewed manifest, no arbitrary paths/URLs/commands/module loads, no token arguments or API-secret reads. Codex receives no unrestricted root/sudo role and no operator signing capability.

Approval binds: contract/release/source/config/unit and dependency hashes; Gate5-equivalent startup approval; predecessor archive and one successor reservation; exact V3 epoch/profile/resources; PID plus start tick, boot ID and systemd InvocationID; one-time service challenge, expiry and unique nonce; expected accepted high-water and checkpoint digest; action, operator-key identity and, for AUTHORIZE_ONE, global ordinal/transport/Core-owned session/request commitment. Do not use low-entropy plaintext prompt hashes as public evidence; a private keyed commitment or protected manifest binding needs separate review. No credential or request content is logged.

The helper verifies protected paths and service peer UID/PID/process-start/boot/invocation over the fixed private AF_UNIX socket. Runtime verifies helper peer and signed approval, rechecks source/config/runtime/epoch, D06 clean, no conflicting actor, zero accepted set for initial OPEN, fresh startup checkpoint and nonterminal state immediately before durable commit. A fixed caller identity alone cannot select an arbitrary epoch or backup. Runtime revalidation prevents stale preflight/TOCTOU from becoming authority. Unknown, corrupt or missing state refuses without initialization.

OPEN commits operator audit before acknowledging HOLD; HOLD cannot admit a request. AUTHORIZE_ONE is distinct, single-use and bound to the next approved ordinal. Permit consumption and accepted ID are durable in one transaction before any provider work. A client only matches an already armed permit; it cannot create one. Authenticated continuation retains the reviewed REST header/WS control scope and reuse semantics, but never serves as an opening grant. Bind it additionally to the active Core-owned V3 session/runtime/epoch. Do not silently change reusable continuation handles into one-use credentials; permits are separate objects.

The actual opening event records durable authorization, runtime acknowledgment and accepted work as different facts. Repeated/expired/wrong-runtime/wrong-epoch actions refuse; no retry on ambiguous commit. Restart invalidates runtime authority, not accounting. Manual stop/abort/uncertainty permanently revokes permits, prevents all later admissions and drains only within30seconds while preserving remote unknown. A tool proposal from either lane aborts without dispatch. No remote stop authority is added by this design.

Root, kernel, system supervisor and protected helper implementation are trusted. A compromised service could emit false local audit; independent root-protected operator records, source manifests and state verification reduce this risk but do not prove an uncompromised kernel. Signed approval does not protect jarvis-writable source; identity and release protections must be deployed together. If user-presence credentials or distinct identities are unavailable, strong separation is blocked; do not silently substitute workflow-only same-UID access.
