# Identity separation and access matrix — proposed, not provisioned

Actual current metadata: jarvis UID/GID1000, home0750, repository/data0775, D06/controller/backup roots0700, D06 state/managed marker0600, no inspected ACL entries. The service and Codex's Core SSH identity share jarvis. Unix0600 does not distinguish them. A root-owned file beneath a jarvis-writable parent is also insufficient: the parent permits substitution/rename.

Proposed identities: a non-login `jarvis-pilot` service UID; a distinct human `jarvis-pilot-operator` identity using credentials unavailable to Codex; a fixed root-owned control/deployment helper; system systemd as supervisor. Names/UID allocation require approval. No new account, ACL, unit, sudo/polkit grant or ownership change was made.

Rights: R read, W write/create, X execute/traverse, – denied. Root/kernel remain trusted and can bypass ordinary DAC; the helper column describes its reviewed code's permitted actions, not a claim that root lacks other OS powers. Human access to secrets occurs only through a separate provisioning ceremony, never through Codex.

Protect executable interpreter, venv/site-packages, startup imports, working directory, configuration parents and Python search paths together. No PYTHONPATH/PYTHONSTARTUP, writable plugin directory, user site or jarvis-owned symlink enters the release. A separate UID with jarvis-writable code is not separation. Keep service sandbox writable paths enumerated, no supplementary groups granting operator authority, no shell/ambient capabilities, no service permission to manage system units. The exact system-unit sandbox requires isolated compatibility tests; this task installs nothing.

The current user unit cannot simply switch User to the proposed UID through its unprivileged user manager. Use a newly approved system-supervised unit, Restart=no/autostart disabled/UMask0077, fixed executable/working directory and protected artifacts. Old user unit remains disabled and is never automatically restarted. Port8000 collision and old writer release are checked after authorized retirement, before new startup.

## D06 migration is a fenced transfer, not a second ownership domain

Existing `_private` checks require owner==geteuid, mode0700/0600, regular single-link files and no symlinks. Backup/controller readers similarly bind ownership. New UID cannot transparently read current stores. Do not weaken these checks globally, grant broad ACLs or recursively chown the repository/home.

After V2 final closure only, a separately authorized privileged procedure verifies no live V2 writer/lease/unknown, records exact source metadata and takes a fixed migration lock. Copy verified D06 scope/state/managed-marker **bytes unchanged** into a protected staged new authoritative root with explicit per-object new owner/modes; never call provision/reset/release. Preserve old namespace as retired evidence. Fsync, verify hashes/scope, then publish one root-protected migration manifest selecting the new active root. New release refuses without that exact authority; old release is not eligible to run. Preserve lock/marker associations in the migration manifest; a copied lock inode is not evidence of holding the old lock. Verify quiescence before transfer and exclusive new writer before readiness.

Any failure leaves both new admission and migration publication closed; retain partial artifacts. No automatic fallback to old namespace, no copy of live SQLite files, no second independent coordinator, and no migration when current/last/unknown differs from approved clean state. Proposed relocation from jarvis's writable home to `/var/lib` changes frozen paths and needs approval. Changed resource/model for a legacy adapter needs a separate qualified ownership design; Granite's existing D06 scope cannot silently cover it.

Old processes and arbitrary network clients can ignore local D06 entirely. A migration manifest is not an endpoint firewall. Explicitly contain all known old/new callers during the pilot window; root/hypervisor/external actor assumptions remain documented. If this cannot be established, opening is blocked even after filesystem separation.

Legacy archive validator: retain the exact V2 content/schema/association rules, but use a new explicit read-only archive mode accepting only a root-owned pinned archive under protected ancestors with prescribed modes/group. Validate recorded original ownership metadata separately from current archive-copy ownership. Never relax live V2 `_private`, rewrite legacy manifests to new UID, or let a service-supplied owner value authorize arbitrary files. V3 live/checkpoint validators are separately versioned and tested.
