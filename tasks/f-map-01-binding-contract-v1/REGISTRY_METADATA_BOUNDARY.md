# Passive registry-metadata boundary

Core registry currently has `_EXPLICIT_TOOL_MODULES` and a private `_tool_modules` map. `list_tools()` calls `_load_tool()` for each key, importing handler modules and logging load failures. It is **not** a pure, immutable metadata API suitable as a producer dependency. `get_tool()` also loads a module. `call()` executes and is forbidden. The current source can be inspected statically; this task did not call registry discovery or execution.

Future boundary contract: a separately built immutable `RegistryMetadataSnapshotV1` supplies exact declared key, module path, handler `SAFETY_LEVEL`, supported V1 handler fields/actions, and for `apps` the declared `_APP_MAP` key set. It is produced from audited JARVIS-owned registry/handler declarations **before** projection creation, with no `execute`, `registry.call`, tool instance, callable or loaded module in the snapshot. Its source revision and deterministic content digest are carried alongside it. `binding_projection.py` only reads that supplied snapshot and requires exact V1 rows; metadata cannot add a new V1 action. Building/exposing the passive snapshot is future implementation work, with its own no-side-effect test. No public API/path is claimed to exist today.

At Core HEAD, static AST inspection proves the two explicit keys, handler `execute` and safety levels (`apps=0`, `browser=1`). This evidence is in the sealed `registry-static-inventory.json`. The snapshot boundary must fail closed if a declaration, module path, handler shape, allowlist, source revision or digest differs from this reviewed V1; it may not fall back to live `list_tools()` or dynamic discovery.
