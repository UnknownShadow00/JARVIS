## r4 control flow and disk-write boundary

All source references below are exact files extracted read-only from retained Subiquity snap **7403**, SHA256 `ee9467fec724cf2a7f4fc61641a4a05d84f7730f06b8fefaceaf0b51a9a0331b`. Sources and hashes are indexed in [source-record.json](evidence/source-record.json). The snap identifies Subiquity 26.04.1; its manifest pins curtin commit `ab0c9258d481182ba024445261fdc4dd501cd321`. This is stronger evidence about the retained media than current documentation, but the actual running revision still needs confirmation.

1. `server.py:1034–1061`: load controller objects and start the API server; wait for cloud-init; select effective autoinstall; load early configuration. Cloud-init and the live boot environment run **before** this hook. Controller construction/API availability is not a global storage exclusion mechanism.
2. With configured early commands and **no** `/run/subiquity/early-commands` success stamp, `start()` awaits `Early.run()`. `cmdlist.py:57–107` checks command exits; a direct argv command is wrapped for journal output through `systemd-cat`. A Python uncaught exception exits nonzero and propagates as `AutoinstallUserSuppliedCmdError`. A failed first command does not create the success stamp.
3. Only after successful early execution (or skipping it because the stamp already exists) does `start()` reload all configuration, restore state, start controllers through `super().start()` and apply autoinstall. `core-application.py:115–125` starts controllers; `filesystem-controller.py:2390–2400` schedules probing; `install-controller.py:102–104` creates the install task. Successful early execution is cached across server restarts within the same live `/run` state. An ordinary reboot normally loses that state; do not assume an earlier boot's stamp survived.
4. `install-controller.py:608–661`: wait for required configuration and confirmation, prepare sources/packages, optionally unmount an existing target, then call `curtin_install`. A kernel `autoinstall` argument can auto-confirm. The retained GRUB configuration itself has no such argument; actual `/proc/cmdline` and operator interaction are unknown. Do not count on an interactive confirmation as a safety barrier.
5. `install-controller.py:338–435`: initial curtin call has `stages=[]`; the ordinary direct-layout path then explicitly calls `stages=["partitioning"]`, followed by extraction and later curthooks. The partitioning call includes rendered storage actions. **It can create partition tables AND filesystems AND mounts.** A separate step named `formatting` belongs to a different snapd/core path; absence of that name does not mean no mkfs ran.
6. `curtin-block-meta.py`: `meta_clear:2219` can tear down holders before storage handlers; disk/partition handlers can wipe/create partition tables, and `format_handler:1206–1222` calls mkfs. Custom actions run in order (`meta_custom:2237–2313`). The earliest destructive operation can precede mkfs and target mounting. There is no transactional rollback restoring the original disk on a later error.
7. `curtin-runner.py` and `runner.py:62–92`: curtin executes through transient `systemd-run --wait` units. The server's wait is ordering for its own request, not an interprocess disk lock. The storage call specifies `private_mounts=False`, but the operator's diagnostic command/namespace is unknown and a past mount may have ended. A root shell or failed guard does not prove that every earlier transient unit has exited.

The embedded guard itself uses UUID/network reads, `udevadm settle`, `lsblk`, `udevadm info` and `wipefs --no-act`. It has no partition/format/write invocation and no lock, kernel write protection, service exclusion or cancellation of other writers. It fails at uniqueness **before** its signature query when the supplied partitions are visible. Thus this failure reports observed topology; it cannot establish when the bytes were written. Udev identifier inheritance does not create GPT or ext4. In-memory Subiquity model methods called `create_partition`/`reformat` must not be confused with on-disk curtin execution (`manipulator.py`, `filesystem-controller.py:679`).

Canonical's [autoinstall reference](https://canonical-subiquity.readthedocs-hosted.com/en/latest/reference/autoinstall-reference.html#early-commands) documents early-command ordering before normal device probing; its [validation sequence](https://canonical-subiquity.readthedocs-hosted.com/en/latest/reference/autoinstall-schema.html#how-the-configuration-is-validated) describes the subsequent reload. Curtin's [stage documentation](https://curtin.readthedocs.io/en/latest/topics/config.html#stages) distinguishes its own early stage from partitioning. **Subiquity's explicit stage selection in 7403 means merely adding a curtin `early_commands` entry would not protect this partitioning call.** These current docs are corroboration, not proof about VM164's execution.

## Root-cause separation

**Confirmed software root cause of the refusal:** r4 flattens `/dev/sda`, `/dev/sda1`, `/dev/sda2` and all other devices, then demands that each expected udev value have exactly one owner `/dev/sda`. Partitions legitimately inherit the parent identifier. This incorrectly treats inheritance as a collision. The error also hides the subsequent, correct refusal of an already initialized target. The previous synthetic suite checked partitions only for any refusal, so the wrong reason passed; it lacked a positive partition-inheritance identity test paired with a negative virgin-admission test.

**Confirmed design limitation:** the early command provides admission ordering in one normal installer instance. It is not disk write protection and does not serialize cloud-init, initramfs/live services, other installers, transient curtin jobs, root shells, or host-side writers. The exact first invocation in the pinned normal path must finish successfully before that instance starts its install controller. Therefore the claim “this first early command failed, then this same normal instance proceeded to partition anyway” is **not supported by this source trace**. A code/config/version difference, separate/prior invocation or another writer would need evidence.

| Remaining explanation | Why plausible / limits | Evidence needed |
|---|---|---|
| Earlier successful automatic attempt, followed by failure in a later automatic invocation | A blank disk would pass r4; direct layout can then create the observed BIOS/GPT/ext4 shape. A later invocation observing those partitions would fail. No earlier PASS is supplied. Same-state restarts with a success stamp normally skip the hook, so this hypothesis also needs a different state directory, missing/reset stamp, another server instance or another boot/config transition. | Full per-PID journal, PASS/error times, boot IDs, stamp metadata and server lifecycle |
| Another or surviving curtin/installer process | Commands run as separate systemd jobs; a failing new guard does not cancel a prior writer. This is a supported possibility, not evidence such a job existed. | Transient unit InvocationID/cgroup/PID, effective configs, start/finish timestamps and curtin command records |
| Different effective config/media/runtime or modified startup path | `server.py:941–983` prioritizes CLI, kernel path, live-root and cloud config over ISO YAML; config is reloaded. Refresh disabled in the retained YAML is not proof of actual runtime. | Mounted media hashes, running snap revision/exe, effective `/autoinstall.yaml`, argv, cmdline and config-selection logs |
| Pre-hook live boot/cloud-init/custom service or external writer | The hook follows cloud-init; boot/udev/other privileged processes and host access are outside its protection. No specific such writer is identified by retained evidence. | Cloud-init/module configs and logs; live services/udev rules/processes; hypervisor task and volume access history |
| Preboot check did not cover the same effective bytes/time interval | Trusted check accepted as reported. Exact backing-volume mapping, offsets, scan coverage and the interval after the check remain uncorrelated. | Raw timestamped check, volume resolution/format/backing chain and exclusivity records tied to the observed disk |

The observed shape is consistent with guided direct BIOS installation (`boot.py:172–190`, `guided_direct:679`) and is useful for comparison with curtin configs. It is not a writer fingerprint or proof of installation completion. The automatic-failure clarification rules out manual guard execution as the source of this traceback; it does not establish this was the first server/guard invocation in the boot. A raw-log timeline is the next discriminator. No target mount in one observation excludes neither earlier formatting nor earlier extraction.

## Disposition and next action

Retain the current disk as evidence. **No in-place retry, wipe, resume, repair, boot-to-target or relaxed signature/partition check is defensible under the current authorization.** Installation and readiness remain NO-GO. A new separately approved blank disk is the recommended eventual installation target, with a newly approved hardware serial/identity binding and a fresh exact single-disk plan. The original evidence disk must not be co-attached to the installation environment; its later preservation/isolation requires separate explicit authorization because detachment/lifecycle changes are currently forbidden. Another disposable VM could preserve VM164 untouched, but requires its own identity/resource approval and is not authorized here.

Forensic examination of an approved evidence copy is defensible; recovery or sanitization of the original is not justified by this evidence. Neither a live copy nor a crash-consistent snapshot automatically proves a stable forensic image. Any later consistent acquisition must have a separately approved method, backing-chain accounting, timestamps and hashes. Until then leave VM164 running in its failed state and VM163 stopped.
