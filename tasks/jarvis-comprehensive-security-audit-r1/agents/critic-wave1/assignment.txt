JARVIS is a single-operator Python/FastAPI desktop/headless assistant with REST, WebSocket, PWA, Electron and hologram clients, local Ollama inference, file/shell/computer tools, optional memory services and outbound bot notifications. Authority stores task/schedule/receipt/outbox state in SQLite. Privileged resources include local files/tools, task state, HMAC checkpoint anchors, enrollment custody, operator permits and proposed Proxmox serial access. There is no source-grounded comparable security baseline.

HTTP authentication uses one configured Bearer token. Empty token is permitted for loopback configuration and bypasses ordinary HTTP and WS credential checks. Remote configuration requires a token; this validates configured bind host, not incoming Host. CORS is configured; both WS paths separately validate present Origin. Ordinary authority routes use fixed Actor(local-service). Operator diagnostics independently requires a configured token. No multi-user isolation is promised. Browser, local untrusted process, authenticated client, untrusted artifact supplier, separately restricted OS UID and operator are distinct principals.

The ordinary runtime opens data/authority/queue.sqlite without a ledger, enrollment witness or legacy permit. Mandatory startup therefore fails closed for missing/enrolled/legacy stores unless trusted embedding explicitly supplies an admitted authority. TestClient tests bind synthetic authorities and often skip lifespan. Do not equate isolated route reachability to a working stock deployment. Synthetic execution requires trusted opt-in and exact synthetic executor types; no real executor activation is authorized. Legacy chat tools are a distinct live-capable dispatch path gated by safety level, confirmation and dry-run.

Important chains: HTTP/WS chat -> classifier -> deterministic tool parameters -> registry -> files/shell/browser/computer; tool output -> later LLM prompt. HTTP tasks/schedule -> service actor -> durable receipts and transactions -> scheduler/outbox -> synthetic execution. Operator descriptors -> permit/context authentication -> enrollment, checkpoint rollover, archive verification, disposable restore, recovery decisions and branch checks. Archive inputs are directory/JSON/SQLite bundles, not general tar extraction. Inspect recovery_decisions.py, which is present in the capture.

SQLite uses lifetime flock, generation ownership, inode checks and poisoned instances on uncertain writes. Ledger adds HMAC-authenticated append-only checkpoint intents/finals, rollover epochs, state bounds and external trust context. Application file helpers check leaf type/UID/mode/link count and symlinks but use absolute path operations. Distinguish same-UID trusted control from other-UID ancestor replacement, whose filesystem prerequisites need evidence. Proposed infrastructure securefs uses descriptor-relative all-component traversal and ownership checks.

Proxmox phase2 is observation/planning, and phase3 src/g6k_serial is a proposed VM164-only serial broker/worker with fixed inspection catalog, SO_PEERCRED identity, root-controlled activation/grants, durable request/session identities, TLS/VM checks, separate service accounts and seccomp/systemd designs. No actual installed identity/ACL, no-NIC, unit, grant, transport or privileged Gate6K qualification is established or tested. No production actions or provider calls are permitted.

Deployment sources are app/main.py, Dockerfile/Compose, .github workflows, client launchers and infrastructure units. Compose publishes host loopback, but binds backend 0.0.0.0 inside the container. Dependencies float; actual installed versions and deployed controls are unknown. No dependency installation or whole-suite test is allowed.
